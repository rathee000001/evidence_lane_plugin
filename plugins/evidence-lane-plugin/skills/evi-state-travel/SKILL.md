# Evidence Lane current State Travel

Run only on explicit user request or genuine host-context exhaustion. Use one
genuinely fresh native same-project destination, never a fork, reconstructed
chat, helper task, renderer restart, or historical accepted-folder fallback.

The current workflow is direct-only:

1. In the destination, display the complete native destination identity before
   any Evidence Lane read.
2. Read this installed skill and
   `../evi/references/mcp-tool-routing.v1.json`.
3. Run `runtime_doctor`, `session_flash_status`, `session_resume` with the exact
   destination UUID as `host_session_id`, and `runtime_activation_status`.
4. Call the public six-field
   `pv_state_travel_direct_force_same_worktree` exactly once with project,
   governed session, authoritative source task, runtime donor task, destination
   task, and visible destination title. The server derives every volatile
   source, pointer, Plan, runtime, Flash, package, profile, and replay value.
5. Present the full receipt, then the small whole-Plan native gate. Stop for the
   user’s visible **Implement this plan** acceptance.
6. After the distinct acceptance receipt, run one atomic native
   acceptance/Goal-resume transaction. Its embedded unchanged-Plan identity
   guard is not another EVI Plan invocation or whole-Plan update. Resume the
   one carried Goal first, then relock exactly the persisted header plus fixed
   Step Task List window and unchanged Changes attachment.

EVI Plan runs exactly once in the destination: it returns the small
whole-authority prompt that produces the visible Implement control. After the
user accepts, never insert another EVI Plan verification phase, prompt, or
whole-Plan projection between acceptance and Goal resume. Only the fixed
header plus current persisted batch is projected after the Goal is RUNNING.

The source task and destination have distinct closeout roles. During handoff,
the source task may temporarily show only the native State Travel checklist;
this does not mutate canonical Plan or the fixed Step projection. The source
waits until the destination has all three receipts: Implement acceptance,
carried Goal RUNNING, and fixed Step/Changes relock. Only then it uses the
reset-aware rich Goal route, appends the exact source segment to the
ChatLineage Goal sector, displays current and formula-backed consolidated
tables, consumes the human option-2 completion exactly once, and marks only
the source Goal achieved. Any source-task steers arriving after State Travel
was requested are sent to the destination once, in one consolidated steer
that includes the Goal-log steer, and only after destination Goal resume. The
destination remains sole writer throughout.

An existing Project candidate, pending HIL, and pending task are integrity-
checked and preserved byte-for-byte. They are never cleared, rebuilt, renamed,
or required to equal later live-root changes. Pointer, Plan, dirty worktree,
identity, replay, and integrity violations remain fail-closed.

Sealed prepare/resume compatibility routes are absent from the installed
surface. The only current attachment route is native `session_resume` followed
by the six-field direct route. State Travel never
restarts Codex and never launches a helper.

The only Step Task List projector is the content-addressed canonical header plus
persisted fixed window. Sliding, fixed-9-without-header, verbose, duplicate,
thread-history, and fallback projectors are obsolete and non-executing.
State Travel uses the native verification and Plan receipts only; it never
calls `render_runtime_panel` or `render_project_panel`.

Goal completion and State Travel remain separate. Only the human’s exact Goal
completion disposition can close the source task. Completion telemetry uses
only the reset-aware rich Goal route; no compact compatibility collector is
present. It does not imply HIL, Fuse, pointer, Git, or install authority and
never implies HIL approval.
The exact completion command is `MARK GOAL COMPLETE` with either
`COMPLETE_THIS_TASK_AND_STATE_TRAVEL` or `COMPLETE_FULLY`. Render telemetry only
through `build_rich_goal_completion_metrics_receipt`.

Post-entry Plan authority reads use bounded `pv_status`, `pv_task_backlog`, and
`pv_query` only after the direct entry PASS; they never open accepted storage.
After the carried Goal is RUNNING, use host `update_plan` only to relock the
single canonical fixed Step projection; never use it for a second EVI Plan.

Before hardening or reconstructing a State Travel rule, query the live
ChatLineage FTS5 slice first. On a no-hit, use its bounded direct SQLite/JSONL
fallback, then refresh/refire through the normal Delta-exit authority sequence;
never widen to accepted ZIP storage. Accepted ZIPs are snapshot-only and are
not entry, model-context, Plan, Goal, Learning, or State Travel sources.
